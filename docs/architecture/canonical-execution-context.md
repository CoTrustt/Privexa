# Canonical Execution Context

`ExecutionContext` is Privexa's immutable, server-established authority envelope for one protected
operation. Authentication establishes the human identity, `AccessControlService` establishes one
bounded permission and validated Firm/Client scope, and the FastAPI authorization dependency issues
the context. Application services receive it explicitly.

```text
request UUID
  + authenticated principal
  + current membership and role
  + authorized Firm/Client scope
  + one granted Permission
  + server origin and sensitivity policy
  + optional trace ID
    -> ExecutionContext
    -> application service
    -> FirmContext/ClientContext projection
    -> repository and PostgreSQL RLS
```

The current HTTP issuer assigns `WEB` as the originating channel and begins at the server-controlled
`STANDARD` effective sensitivity. The application request ID is generated by Privexa. `trace_id` is
absent until a valid tracing integration can supply the current W3C trace; it is never synthesized.

When protected information enters the operation, `with_minimum_sensitivity(...)` returns the same
trusted context or a new frozen trusted context at the most restrictive applicable level. It never
mutates the original context and never reduces sensitivity. See `data-sensitivity-policy.md` for the
domain rules.

The existing action-bound authorization contexts are internal authorization results. `FirmContext`
and `ClientContext` remain narrow repository/RLS projections. Neither is an alternative canonical
execution envelope. The database Session must already contain the matching final tenant scope, and
services fail closed when the Session and `ExecutionContext` disagree.

## Trust rules

- Never construct authoritative execution contexts from request headers, query parameters, bodies,
  cookies, serialized contexts, model output, or arbitrary IDs.
- Never add passwords, tokens, cookies, provider secrets, database credentials, full ORM entities,
  or raw authorization evidence.
- Capabilities are immutable `Permission` values issued by deterministic authorization policy. LLM
  or agent output cannot add, reinterpret, or expand them.
- Effective sensitivity is immutable and monotonic. Only typed server-validated resource metadata
  may raise it; request data, LLM output, and agent output are not security authorities.
- Do not log the model itself. Use its explicit safe logging projection and add event-specific data
  separately.
- The in-process context lives for one request. Workers must later carry a separately validated
  envelope and reauthorize when execution starts; serialized Pydantic data is not trusted authority.
- A future AI Gateway may consume the context as a policy input but must derive a narrow model-safe
  scope instead of dumping the raw context into a prompt.
- New authority-bearing fields require a documented server-side source and validation authority.

Commercial entitlements may later constrain authorization before a permission is issued. Billing
identifiers and subscription implementation details do not belong in `ExecutionContext`.
